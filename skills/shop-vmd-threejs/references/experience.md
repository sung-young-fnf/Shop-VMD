# 매장 탐색 UI와 렌더링

## 참고 웹사이트에서 가져올 것

WebGL 사이트는 실제 브라우저에서 초기 화면과 진입 후 화면, 드래그·줌·선택·키보드·모바일을 확인한다. DOM의 computed style로 UI 토큰을 기록하고 3D 장면 관찰과 구분한다. 관찰한 것, 직접 조작한 것, 추정한 것을 분리한다. 흰 캔버스만 캡처됐다고 사이트 자체가 비어 있다고 결론내리지 않는다.

Ciudad Jardín에서 적용한 교훈은 큰 디오라마, 작은 부유형 패널, 장소 선택에 따른 카메라 이동, 하단 보기 도구였다. 이 사이트는 GLB를 사용하지만 원본 모델을 이번 절차적 집 모델에 복사하지 않았다. 매장에서도 참고 사이트의 조작 구조와 자체 브랜드·모델을 구분한다. 사용자가 요청하지 않은 도시 운전·주택 조경 기능을 따라 만들지 않는다.

UI 구현 전에 프로젝트 `DESIGN.md`에 색상·타입·간격·컴포넌트·상태·모션·반응형 규칙을 둔다. 크림색·세이지 팔레트는 기존 주택의 선택이지 모든 브랜드 매장의 규칙이 아니다.

## 보기와 선택

전체, 실내, 평면, 천장/전면벽 절개 중 필요한 보기를 구현한다. 선택은 `none`, `zone`, `fixture`, 필요시 `product`를 명확히 구분한다. DOM 목록에서도 같은 대상을 선택할 수 있게 한다. 숨긴 천장·조명 레일·상부 벽이 선택 결과를 가리지 않아야 한다.

포인터를 놓을 때 이동량이 클릭 허용 범위보다 작을 때만 raycast한다. 허용값은 프로젝트 조작 환경에 맞춰 정하고 드래그·터치와 함께 시험한다. 현재 보기에서 가려진 대상이나 장식 메시가 의도한 집기보다 먼저 선택되지 않게 한다. 안내문도 해당 보기에서 가능한 조작을 설명해야 한다.

선택 대상의 bounds와 중심에서 카메라를 계산하고, 필요하면 보정된 시점을 사양에 둔다. 모든 카메라 목표 거리를 OrbitControls의 min/maxDistance와 일치시킨다. 작은 방의 목표 거리가 최소 9m보다 짧아 보간이 끝나지 않았던 문제가 있었으며, 기다리는 시간을 늘리는 대신 목표 거리를 보정해 해결했다. 9m는 사례 값이며 매장에 그대로 적용하지 않는다.

모든 존·집기를 하나씩 선택해서 최종 화면을 본다. 주택의 Flex Room은 선택 이벤트와 UI 변경은 정상인데 굴뚝이 화면을 가렸다. 매장에서도 기둥·행거·사인 때문에 같은 문제가 생길 수 있다. 대상별 시점 보정이나 의도된 절개로 해결하며, 선택 상태만 검사해서 통과시키지 않는다.

다층 매장은 지붕·천장뿐 아니라 상층 바닥도 아래층을 가린다. 바닥에 층 식별자를 두고 선택한 층 위의 바닥을 절개 대상으로 구분한다. 창고를 선택했을 때 랙이 실제 보이는지 확인하고, 전체 보기로 돌아오면 원래 가시성을 복원한다.

출처 패널의 페이지 범위와 설명은 검증된 사양을 기준으로 연결한다. 집기 이름이 비슷하다는 이유로 다른 상세도 페이지를 수동 복사하지 않는다. 자료에 없는 판매 구역이나 확정되지 않은 재료를 UI 문구에서 사실로 승격하지 않는다.

## 모바일·키보드·실패 상태

패널이 매장 전체를 가리지 않도록 모바일에서는 축소 메뉴, 가로 목록, 하단 시트를 사용한다. 캔버스 aspect와 실제 여유 영역으로 화면 맞춤을 계산한다. 데스크톱 카메라 거리만 그대로 쓰면 좁은 화면에서 매장이 잘린다. 고정된 스크롤 패널은 크기·최소 높이·스크롤 소유자를 지정한다.

폭 분기만으로 휴대폰 가로 화면을 처리하지 않는다. 낮은 높이에서는 상단 존 목록과 하단 정보 카드가 겹칠 수 있으므로 패널 크기·위치와 카메라 여유 영역을 높이까지 고려한다. 가로 overflow가 없어도 모델이 가려질 수 있다. 동일한 폭 분기 안에서 세로·가로 방향이 바뀌어도 현재 보기를 다시 맞춘다.

버튼과 선택 상태에는 접근 가능한 이름, focus 표시, 의미에 맞는 ARIA를 제공한다. 한국어 줄바꿈과 한 글자 고립을 실제 화면에서 확인한다. 낮/밤 테마를 제공한다면 색상 변수를 바꾸는 요소에서 실제 foreground 상속도 확인한다. 주택에서는 루트에서 이미 계산된 글자색이 body의 밤 테마 변수를 따르지 않아 대비 문제가 났다.

Reduced motion에서는 자동 회전과 불필요한 이동을 끄거나 카메라를 즉시 이동한다. WebGL 생성 실패·context loss에서는 로딩을 끝내고 원본 도면·재시도를 제공한다. 작동하지 않는 3D 메뉴와 빈 도구 모음은 실패 화면에서 제거한다. 사양 목록의 공간을 미리 확보해 초기 UI 레이아웃 이동을 줄인다.

## 렌더 비용과 자원

렌더 루프는 하나로 관리하고 숨겨진 문서에서는 멈춘다. 정지 화면은 dirty 상태·카메라 이동·damping이 남아 있을 때만 렌더한다. 교체한 geometry/material/texture와 controls, observer, 이벤트, animation frame을 정리한다.

카메라 초기 구도를 계산하기 전에 렌더러를 실제 호스트 크기로 설정한다. 기본 캔버스 크기로 모바일 분기를 먼저 실행하면 첫 프레임 이후 불필요한 카메라 이동과 반복 렌더가 발생한다. 첫 `sceneReady` 시점의 실제 카메라와 정착 여부로 확인한다.

`pagehide`가 페이지의 영구 종료를 뜻하지는 않는다. 뒤로가기 캐시의 `event.persisted` 경로에서는 렌더러·컨트롤을 파기하지 않고 복원 시 프레임 시간과 dirty 상태를 갱신한다. 검증 브라우저가 뒤로가기 캐시를 비활성화할 수 있으므로 실제 `pageshow.persisted=true`와 같은 페이지 인스턴스 복원을 확인한 뒤 보기 전환을 조작한다. 단순 재로드 성공을 캐시 복원 성공으로 기록하지 않는다.

동일한 집기는 InstancedMesh로, 움직이지 않는 상세는 동일한 가시성·이동 그룹 안에서 재질별 병합으로 줄일 수 있다. 선택 가능한 대상의 ID, 천장 제거와 집기 이동 기능을 잃지 않는다. 주택에서는 장면 호출 수가 약 1617에서 463으로 줄었지만 이 숫자는 매장 공통 예산이 아니다. draw calls와 triangles는 렌더 패스·카메라·기기 조건과 함께 기록한다.

`compileAsync`나 작업 분할을 넣었다는 사실만으로 성능 개선을 주장하지 않는다. 실제 Chrome의 동일 조건에서 초기 로딩과 프레임 시간을 비교한다. 주택 작업에서 compileAsync 제거 비교는 개선이 없었고 모바일 초기화 부담은 남았다. 성능 점수를 위해 필요한 3D 장면이나 기능을 숨기지 않는다.
